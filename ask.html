Ask

Semantic search over my portfolio, running entirely in this tab. A sentence-transformer turns your question into a vector, compares it against the passages on this site, and shows the closest ones. Nothing is sent anywhere — there is no server to send it to.

Search

The model is 16 MB and the WebAssembly runtime 3 MB, so neither loads until you ask for it. Your browser caches both, so this is a one-time cost. The passages are already indexed; the model is here to read your question, not this site.

How it works, and what it deliberately is not

The library is Transformers.js, running all-MiniLM-L6-v2 quantised to 8-bit through ONNX Runtime on WebAssembly. Every piece of it — the library, the runtime, the tokenizer and the weights — is served from this domain. Nothing is fetched from a CDN or a model hub at runtime, which is what lets the claim above be literal rather than approximate: the question is tokenised, embedded and compared in this tab, and no network request carries it.

It runs on one thread, and that is not a choice. Multi-threaded ONNX Runtime needs SharedArrayBuffer, which needs cross-origin isolation, which needs COOP and COEP response headers. GitHub Pages cannot set headers, so crossOriginIsolated is false here and threads are unavailable no matter what the config asks for. The interesting part is that it does not matter: embedding one short question is a few tens of milliseconds single-threaded.

The search is a linear scan, on purpose. There is no HNSW graph, no IVF index and no vector database, because at this size every one of them would be slower and all of them would be worse. The status line above tells you how many passages are indexed; a few dozen at 384 dimensions is under ten thousand multiply-accumulates per query, which is microseconds — the measured search time it reports is almost entirely the model embedding your question, not the search. An approximate index is a trade: you spend build time, memory and exact recall to avoid a scan that has become expensive. Here the scan has not become expensive, so the trade is all cost and no benefit. The crossover is somewhere around a hundred thousand vectors, four orders of magnitude away.

It retrieves; it does not generate. What comes back is the passage I actually wrote, with its similarity score, linked to where it sits on the portfolio page. There is no language model writing prose about me, which means there is nothing here that can invent a credential. The honest limitation of that: it answers "what did he do with IoT" well and "would he suit a fintech CTO role" badly, because the second question is asking for a judgement and this only knows how to find the nearest paragraph.

The corpus is this site. Every passage is generated from the portfolio page, embedded once, and committed as a JSON file next to it. The first version of this page did the opposite: it fetched the portfolio, split it up and ran the model over all of it in your browser, to avoid keeping a second copy of the prose that could drift from the first. That was a real concern answered in the wrong currency. It charged every visitor seconds of WebAssembly inference to recompute a value that is the same for everyone, and it quietly made five CSS class names an interface, so renaming one would drop a whole section out of the search while the count still looked healthy. Precomputing turns a silent failure into a loud one: the generator is the only thing that writes the index, and CI fails if a passage in it is no longer on the page.
