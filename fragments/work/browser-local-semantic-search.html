Applied AI This site

The search on the front page of this site answers questions about these projects by running a sentence embedding model inside the visitor's own browser. There is no inference server, no API key and no request carrying the question anywhere. It is small, and it is deliberately small: the point was to build the thing end to end rather than describe having once specified it.

all-MiniLM-L6-v2, quantised to 8-bit, executed by ONNX Runtime on WebAssembly through Transformers.js. Quantisation is what makes the model shippable at all — full precision is four times the weight for a retrieval quality difference this corpus cannot resolve. The runtime runs single-threaded because GitHub Pages cannot send the COOP and COEP headers that SharedArrayBuffer requires, so the threaded build would silently fall back anyway. I measured crossOriginIsolated in the deployed page rather than assuming it.

The model, the runtime and the weights are all served from this origin. The obvious build fetches them from a model hub on first use. That would mean pinning a CDN script by SRI digest in one breath and then pulling tens of megabytes of unpinned executable WebAssembly from a third party in the next — the same integrity problem an order of magnitude larger. Vendoring costs repository size and buys a page with no third-party requests at all, which I verified in the network panel rather than in the source.

Retrieval is an exhaustive cosine scan, not an approximate index. A few dozen passages at 384 dimensions is under ten thousand multiply-accumulates — microseconds, and four orders of magnitude below the cost of embedding the question that precedes it. An HNSW graph would add a dependency, a build artefact and a recall tradeoff to optimise the part that is already free. Knowing where that crossover sits is the engineering; reaching for the vector database before it is the failure mode.

The index is generated by a page, not by a script. Embeddings are precomputed and committed, because asking every visitor's device to embed the whole corpus before answering the first question is a cost paid thousands of times to save paying it once. What that buys is a way for the index to drift from the prose it describes, so the generator runs in a browser, against the same vendored runtime and weights the site ships, which makes the vectors the ones the live code would have produced by construction. A build on a server could not promise that: outside a browser the runtime's backend registry is empty, and a vector computed by a different stack does not raise an error, it just retrieves worse. A check in CI then fails the build if any committed passage stops appearing on this page.

Where this approach stops working, which is the part worth knowing. It is bounded by the download, not by the search. Twenty megabytes is a defensible one-time cost on a page someone chose to interrogate, and it would be indefensible on a page that had to answer before the visitor asked for anything. The linear scan holds to a few thousand passages on this hardware; past that the crossover with an approximate index finally arrives and the honest move is to take the dependency I argued against above. And a 384-dimension general-purpose embedding retrieves topics well and proper nouns poorly, so a question naming one specific system is better served by find-in-page on the portfolio. Knowing which of those limits is nearest is the difference between shipping this here and shipping it everywhere.

The accessibility constraints shaped the code more than the model did. The load button cannot use the disabled property, because disabling the control somebody just pressed moves keyboard focus to the document body, and here it would strand them there for the length of a multi-second download. It sets an ARIA state and guards re-entry with a flag instead. Results are announced through a live region, because focus deliberately stays where the visitor put it. These are the decisions that never show up in a demo and entirely decide whether anyone can use the thing.

  • No inference cost and no data egress — the question never leaves the tab
  • ~25ms per query after a one-time model load
  • Zero third-party requests at runtime
