Ask

Semantic search over my portfolio, running entirely in this tab. A sentence-transformer turns your question into a vector, compares it against the passages on this site, and shows the closest ones. Nothing is sent anywhere, because there is no server to send it to. How it works, and what it deliberately is not, is in the colophon.

The model is 16 MB and the WebAssembly runtime 3 MB, so neither loads until you ask for it. Your browser caches both, so this is a one-time cost. The passages are already indexed; the model is here to read your question, not this site.

How the search works, and what it deliberately is not

The library is Transformers.js, running all-MiniLM-L6-v2 quantised to 8-bit through ONNX Runtime on WebAssembly. Every piece of it, the library, the runtime, the tokenizer and the weights, is served from this domain. No part of it comes from a CDN or a model hub at runtime, which is what lets the claim above be literal rather than approximate: the question is tokenised, embedded and compared in this tab, and no network request carries it. One script on this page does come from a CDN, htmx, pinned to a version and a Subresource Integrity digest so the host cannot change what runs here. It is loaded before you ask anything and takes no part in answering.

It runs on one thread, and that is not a choice. Multi-threaded ONNX Runtime needs SharedArrayBuffer, which needs cross-origin isolation, which needs COOP and COEP response headers. GitHub Pages cannot set headers, so crossOriginIsolated is false here and threads are unavailable no matter what the config asks for. The interesting part is that it does not matter: embedding one short question is a few tens of milliseconds single-threaded.

The search is a linear scan, on purpose. There is no HNSW graph, no IVF index and no vector database, because at this size every one of them would be slower and all of them would be worse. The status line above tells you how many passages are indexed; a few dozen at 384 dimensions is under ten thousand multiply-accumulates per query, which is microseconds, so the measured search time it reports is almost entirely the model embedding your question, not the search. An approximate index is a trade: you spend build time, memory and exact recall to avoid a scan that has become expensive. Here the scan has not become expensive, so the trade is all cost and no benefit. The crossover is somewhere around a hundred thousand vectors, four orders of magnitude away.

It retrieves; it does not generate. What comes back is the passage I actually wrote, with its similarity score, linked to where it sits on the portfolio page. There is no language model writing prose about me, which means there is nothing here that can invent a credential. The honest limitation of that: it answers "what did he do with IoT" well and "would he suit a fintech CTO role" badly, because the second question is asking for a judgement and this only knows how to find the nearest paragraph.

The corpus is this site. Every passage is generated from the portfolio page, embedded once, and committed as a JSON file next to it. The first version did the opposite: it fetched the portfolio, split it up and ran the model over all of it in your browser, to avoid keeping a second copy of the prose that could drift from the first. That was a real concern answered in the wrong currency. It charged every visitor seconds of WebAssembly inference to recompute a value that is the same for everyone, and it quietly made five CSS class names an interface, so renaming one would drop a whole section out of the search while the count still looked healthy. Precomputing turns a silent failure into a loud one: the generator is the only thing that writes the index, and CI fails if a passage in it is no longer on the page.

What a machine checks, so you do not have to trust me

The interesting claim on a page like this is never the design, it is whether anything stops the design from quietly going wrong. Six checks run on every pull request, and each one exists because the failure it catches is invisible on a page that loads cleanly.

  • The palette is written out in four places, in the stylesheet, in the offline 404 page, in the machine-readable design token file and in the browser-chrome colour metas, and a check fails the build if any copy drifts from the source of truth. Contrast is held at 4.5:1 for text against the tighter of the two colour schemes, which is why one accent colour in this system is deliberately not a Catppuccin value: none of them reach the floor as text.
  • The navigation is written out three times, on this page, on the portfolio page and in the offline fallback, because the site has to navigate with no JavaScript at all and a crawler should see the links as content. A check compares the visible labels rather than the URLs, which legitimately differ per page.
  • Every passage in the search index must still exist on the page it was generated from. Editing the prose without regenerating the index would leave a passage describing one thing and its vector describing another, which retrieves worse without ever raising an error.
  • Every project fragment must be exactly what the generator emits. The detail you open in the index above is generated from the portfolio page, so the two cannot disagree. Hand-patching a fragment fails the build.
  • Every fragment an interaction asks for must resolve, and every control that fetches one must keep a stable identifier. A missing fragment is a silent no-op on click rather than an error, and a control that loses its identifier mid-swap sends keyboard focus to the top of the document, which a mouse user would never notice.
  • The design tokens must still parse as design tokens. The colours, type scale and components are described in a machine-readable file, and the build fails on a warning, not only on an error, because a warning there means the file has started describing something that is no longer on the page.

On how this was built

A frontier model wrote most of the code here, and saying so is not the interesting part: in 2026 that is true of most pages, and a model asked for a personal site will hand back the same centred hero and the same carousel every time. This page had one of each until recently. The difference is not what the model can produce, it is what it is asked to hold itself to. The constraints above are the actual artifact: no build step, one first-party script with a written justification, an accessibility rule for every place the obvious implementation strands a keyboard user, and a machine check behind each invariant that a person would otherwise have to remember. Judge the repository, not the hero.
